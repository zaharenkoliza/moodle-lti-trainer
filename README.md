# Практикум по веб-технологиям: Moodle + LTI 1.3

Версия Елизаветы Захаренко на основе каркаса лабораторной: три собственных
вопроса с короткими ответами по JavaScript, HTTP и голосовому интерфейсу.
`q1` спрашивает тип результата `fetch()` (Promise, 3 балла), `q2` — код
«ресурс не найден» (404, 3 балла), `q3` — интерфейс распознавания речи
(SpeechRecognition, 4 балла). Пустой ответ даёт 0 за вопрос. Пробелы по краям
удаляются, подряд идущие пробелы сводятся к одному, регистр не учитывается.
Не строка, лишнее поле или ответ длиннее 200 символов отклоняются как ошибочный
запрос; готовый балл от браузера сервер не принимает.

Проверено локально: `npm test` — 5 pass, 0 fail. Интеграционный тест
использует имитацию платформы; запуск и AGS на реальном Moodle нужно проверить
после развёртывания Node.js, MongoDB и регистрации инструмента LTI 1.3.

Пошаговая инструкция преподавателя опубликована в форуме Moodle
«Создание LTI-компонента» курса «Управление ЭО на веб-платформе 2026».
Основа проекта: Node.js 24+, ltijs 7.0.7, MongoDB 8.0,
один процесс приложения, отдельный HTTPS-домен и Moodle.
Ни LRS, ни xAPI здесь не используются. MongoDB хранит регистрацию LTI,
ключи и историю попыток. Это изменение исходного каркаса: на бесплатном Render
файлы удаляются при остановке сервиса, поэтому попытки перенесены из `data`
в отдельную базу `lti_lab_attempts` того же MongoDB-кластера.

## Быстрый запуск

```bash
npm ci
cp .env.example .env
docker compose up -d mongo
npm test
```

Заполните `.env`: `PUBLIC_URL`, реальные адреса Moodle. Пока `MOODLE_CLIENT_ID`
пуст, приложение работает в режиме подготовки регистрации. Затем:

```bash
npm start
```

Проверьте `https://<домен-тренажера>/healthz`. Зарегистрируйте в Moodle инструмент
LTI 1.3 вручную: URL инструмента `/lti/launch`, инициация входа `/lti/login`,
redirect URI `/lti/launch`, JWKS `/lti/keys`. Перенесите Client ID, Deployment ID
и все адреса платформы из Moodle в `.env`, перезапустите приложение.
В Moodle 3.7 поле открытого ключа принимает PEM: после регистрации получите
`https://<домен-тренажера>/tool-public-key` и вставьте полный PEM в настройки
инструмента. Не вставляйте туда URL или JSON. Ключи сохраняются в MongoDB.

Разрешите сервис AGS для синхронизации оценок, прием оценок и создайте элемент
курса с максимумом 10 баллов и запуском в новом окне. Открывайте его из Moodle
под настоящей тестовой учетной записью студента, записанного на курс.
Прямой переход на `/app` без запуска Moodle дает 401.

## Задание студентам

Авторские вопросы и серверная проверка находятся в `src/grading.mjs`.
Идентификаторы `q1/q2/q3`, веса `3/3/4` и максимум 10 сохранены по контракту
лабораторной. После правки вопросов перезапустите приложение.

Базовое правило: в Moodle передается результат последней завершенной попытки.
Предыдущие попытки остаются в приложении. Повтор отправки сохраненной попытки
не создает новую попытку. Повтор AGS после неоднозначного сбоя может повторно
записать то же значение; это не гарантия exactly-once. Для каждой отправки
используется возрастающий серверный timestamp. Пока есть неподтвержденный
результат, создание новой попытки заблокировано.

Браузер отправляет только `answers` и `requestId`. Пользователь, роли, курс,
ресурс и адрес строки журнала берутся из проверенного запуска LTI. Для POST
также нужны сессия, собственный Origin и CSRF-токен. Сессия длится 45 минут;
после перезапуска приложения необходимо снова войти через элемент Moodle.

## Проверки и ограничения

`npm test` запускает четыре теста расчета и один интеграционный сценарий. Последний
имитирует платформу, создает подписанный запуск, проверяет OAuth-подпись и AGS,
разделение студентов, запрет роли преподавателя, подмену userId, replay nonce
и повтор после сбоя. В тесте используются тестовая память и временные файлы вместо MongoDB.
Обычный запуск приложения всегда использует MongoDB. Реальная установка Moodle
в эту проверку не входит: выполните контрольные сценарии PDF на своем стенде.

Не публикуйте `.env`, `data`, приватные ключи, id_token, ltik и cookies.
Не удаляйте MongoDB-данные во время работы: сменятся ключи инструмента и
потребуется обновление регистрации. Блокировки попыток рассчитаны на один
процесс Node.js. Для нескольких процессов нужны транзакционные блокировки.

## Размещение по примеру Дианы

В корне находятся `Dockerfile` и `render.yaml` для бесплатного веб-сервиса
Render. Нужен MongoDB Atlas M0 и собственный аккаунт Render. Создайте кластер
Atlas, отдельного пользователя БД и настройте сетевой доступ для сервиса.
Передайте строку подключения только в секретную переменную `MONGO_URL` Render,
не добавляйте её в Git. В переменной `PUBLIC_URL` укажите HTTPS-адрес Render
без завершающего слеша. На первом этапе оставьте `MOODLE_CLIENT_ID` и
`MOODLE_DEPLOYMENT_ID` пустыми, заполните остальные реквизиты платформы Gnomio.
После регистрации LTI 1.3 с AGS в Gnomio внесите полученные ID и перезапустите
сервис. Создайте элемент курса с максимумом 10 баллов.

Бесплатный Render может засыпать при бездействии. Первое открытие после паузы
может занять около минуты; если Moodle покажет ошибку входа, повторно откройте
элемент курса после прогрева сервиса. История попыток сохранится в Atlas.

Для нескольких групп используйте отдельный экземпляр и регистрацию на группу.
Несколько студентов одной группы могут пользоваться одним экземпляром.
